# ADR-001: Capas simples para persistencia; el seam de notificacion ya cubre el proximo cambio conocido

## Estado: Aceptado — 2026-11-13

## Contexto
Tras integrar Chain of Responsibility (validacion), Strategy (calculo por categoria) y Observer
(notificacion) en el sistema de solicitudes de reembolso, corresponde decidir si el proyecto debe migrar a
arquitectura Hexagonal completa (puertos e interfaces intermedias para persistencia y notificacion) o
mantenerse en capas simples.

Hechos del proyecto que condicionan la decision:
- No existe ningun plan de cambiar el motor de base de datos (hoy H2 en memoria para desarrollo y pruebas, y
  un unico motor relacional en produccion).
- El unico repositorio es RepositorioSolicitudesJpa, usado por una sola clase (SolicitudReembolsoService).
- Contabilidad si anuncio, para el proximo trimestre, una integracion por API externa para el pago de las
  solicitudes aprobadas. Es el unico cambio de infraestructura con fecha conocida.
- Finanzas menciono ademas un panel interno de metricas como futuro interesado en los cambios de estado.

Criterio de la Guia (6.2): la arquitectura Hexagonal vale la pena en sistemas que sobreviviran 3 anos o mas
con cambios de infraestructura. Se evalua por separado para cada dependencia externa.

## Decision
1. **Persistencia: capas simples.** SolicitudReembolsoService sigue dependiendo directamente de
   RepositorioSolicitudesJpa, sin interfaz de puerto intermedia. Un puerto de persistencia hoy seria una
   abstraccion especulativa (YAGNI): ningun requisito ni fecha la justifica y no hay un segundo
   adaptador que la ejerza.
2. **Notificacion: sin cambios.** ObservadorCambioEstado ya es el seam necesario. NotificadorContabilidad
   puede sustituir su implementacion interna por la llamada a la API externa el proximo trimestre, y el
   panel de metricas se agrega como un observador mas, sin modificar SolicitudReembolsoService ni los demas
   observadores.
3. **Los limites que si existen se verifican con ArchUnit** (ReglasArquitectura, 4 reglas) y se ejecutan en
   GitHub Actions en cada push.

## Consecuencias
Positivas:
- No se agregan interfaces ni mappers de persistencia sin un caso de uso real que los justifique.
- El unico cambio de infraestructura con fecha conocida (integracion de Contabilidad) ya tiene su punto de
  extension listo.
- Los limites de paquetes se protegen de forma automatica en lugar de depender de la disciplina del equipo.

Negativas:
- La entidad SolicitudReembolso lleva anotaciones de jakarta.persistence porque el repositorio JPA trabaja
  directamente sobre ella: el dominio no es 100 % libre de framework. Un puerto con un adaptador y un modelo
  de persistencia separado lo evitaria; se acepta esa concesion de forma consciente.
- Si en el futuro se necesita cambiar de motor de base de datos o de tecnologia de persistencia, el puerto
  debera introducirse retroactivamente; se acepta esa deuda tecnica.
- Un revisor que espere simetria total (puertos en todas las dependencias externas) puede interpretar la
  asimetria como inconsistencia si no lee este ADR.

Senales que harian reconsiderar la decision:
- Un requisito real de cambiar o agregar un motor de persistencia (por ejemplo, una segunda fuente de datos).
- Una segunda implementacion del repositorio, o la necesidad de probar el servicio sin base de datos de forma
  que los dobles de Mockito ya no basten.
- Que el modelo de dominio necesite divergir del modelo de tablas.

## Alternativas consideradas
- Hexagonal completa (puertos de persistencia y de notificacion): descartada por las razones de la decision.
- Puerto solo para notificacion: innecesario, porque ObservadorCambioEstado ya cumple ese papel.
